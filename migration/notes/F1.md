# F1: fast mode (faster than exact, not bit-exact)

User-facing description: `docs/core/FAST_MODE.md`. This note keeps the design decisions, the measurements and the
open issues.

## Design

* `Scene(mode="fast")` returns `heliades.core.fast.FastScene` (`FastSceneMixin` before `Scene` in the MRO,
  `Scene.__new__` picks the class). Exact mode changed only by two hooks with no arithmetic: `Scene._store_cls` /
  `_map_cls` class attributes and `ObjectsMixin._tube_ring_list` (wraps `_tube_rings`); `ForgeBackend(mode)`.
* **Object matrices stay on exact mode's float32 chain**, members are deferred. Reason: object matrices feed the tube
  bakes (nodes/radii the plant code reads back, e.g. peduncle radii in `update_peduncle_radii`); keeping them exact
  keeps every plant-side value exact unless it comes from member geometry. An f64 product per object op would be
  cheaper, but the measured cost of the exact 4x4 chain is small next to the deferred row work it replaces.
* Deviation from the suggested design: tube deferral is not "nodes/radii only, rebuild everything at flush". Helios's
  `setTubeRadii` is path dependent (it rescales along the *current* ring offsets) and `appendTubeSegment` keeps the
  old rings, so the deferred state is a per-node ring radius `c` with `setTubeRadii: c <- sign(c) * r` (keeps a
  collapsed ring collapsed, flips with negative radii like the eager sequence), and a tube leaves this "recipe" form
  when its rings stop being frame rings (rotation bake, girth/length scaling, pruning: the last ring of a pruned tube
  keeps its central-difference frame). Pure translations keep the recipe.
* Targeted flushes (per object / per parent of a UUID list) are what makes the deferral pay: leaf areas are read
  every sub-step (phytomer creation, season bookkeeping, leaf inclination tracking), and a global flush at each read
  would re-materialise every stale tube each time. A global flush happens only through `store.T` (snapshot / export /
  code that reads rows directly); in a library build that is 0-2 times per plant (`fast_stats`, `flush_reads`).
* Same draws: nothing in fast mode draws, and the draw-dependent control flow only reads plant-side values, object
  matrices, tube nodes/radii (all exact) or geometry (the divergent cases below).
* Model-level fast paths that test `ctx.mode` (the plant code otherwise does not know the mode): grape cluster packing
  (any summation order), fruit vertex weld (`allow_chains`), `setPetioleBase` with a zero shift (90 % of the calls in
  the trees). Numba was not added: the remaining time is spread over thousands of small Python functions of the plant
  code, none above ~10 %, so compiling a kernel would not change the picture.

## Why the deviation is what it is (sensitivity floor)

Leaf areas are read from geometry and feed internode girth (pipe model), which moves child-shoot origins
(`0.9 * parent_radius` along the outward axis) and from there every downstream position and angle, with
amplification where angles come from nearly parallel vectors. Exact mode itself is that sensitive:
`fast_survey.py --sensitivity` rebuilds a plant in exact mode with every primitive area moved one float32 ulp (up, then
down) and reports the vertex deviation; it is of the same order as fast-vs-exact for the models with feedback
(table below). Fast mode cannot be closer to exact mode than exact mode is to itself under one rounding of a leaf area.

## Open issues

* Fast mode is not faster than Helios single-process for any of the benchmark models (table above); it is 1.2-2.5x
  faster than exact mode. The remaining time is plant-code Python (per-phytomer bookkeeping, tube frames, season
  logic, parameter structs with C++ value semantics); beating Helios per plant needs that code vectorised across
  phytomers or compiled, which is a restructuring of the plant-architecture port, not a core change.
* `fast_survey.py`'s `struct_rel` uses a floor of 1e-3 in the denominator, so angles near 0 inflate it; `struct_abs`
  (degrees for angles, metres for positions) is the more readable number.
* `plant_structure_dict` raised for plants with build parameters (`<plant_model>`, written only then, was parsed
  as a number); it surfaced for `apple_fruitingwall` (default build parameters). Fixed: `plant_model` is a string tag
  (`heliades/plantarchitecture/structure.py`).
