# S0: declarative species definitions and the first new species

User-facing docs: `docs/species/FORMAT.md` (the format), `docs/species/ADDING.md` (how to add a species). This note
keeps the design decisions, the parity result, what the format cannot express yet, and the trait tables.

## What was built

* `heliades/species/`: `loader.py` (parse, validate, register), `fields.py` (the overridable fields, kinds, ranges),
  `rules.py` (named growth rules), `organs.py` (flower / fruit prototypes), `leaf_texture.py` (procedural leaf
  textures), `assets.py` (asset lookup), `traits.py` (plausibility harness), `defs/*.yaml`, `assets/<species>/*.png`.
* Species files: `cucumber_from_tomato` (Helios's cucumber from the tomato, 0 ulp), `eggplant` (tomato template),
  `barley` (wheat template).
* Parity: `heliades/parity/suites/plantarch/{ops,cases}_species.py`, six cases.
* Tests: `tests/species/` (loader + validation, rules, organs + textures, traits). Gallery:
  `scripts/species/gallery.py` -> `outputs/species/{eggplant,barley,gallery}.png`.

## Design decisions

* **YAML** (`yaml.safe_load`): comments next to judged values, one value per line in flow mappings, JSON is a subset
  (an agent can emit JSON). Trap documented: commas inside unquoted flow-mapping notes split the value (the loader
  reports it as an unknown key).
* **Template, then overrides.** The species initializer runs the template's own `initialize<T>Shoots`, so the
  template's Context draws (the leaf-prototype identifiers) happen exactly as in the library; it then *copies* each
  listed shoot type (copy constructor, no draw), applies the overrides as the C++ statements would (`operator=`,
  `*Distribution`: no draw) and defines the result. That is why a file built on the tomato can reproduce the cucumber
  bit for bit: both draw the same four identifiers. A species built on the same template has the same draw count at
  load as the template.
* **Every set value has a `source`**: a key of `sources` or `judged`. No third option, no default. Values not set are
  the template's and need none.
* **Registration on first load.** `loadPlantModelFromLibrary(name)` registers a species file when the label is not a
  library model (`architecture.py`, 4 lines). `getAvailablePlantModels()` therefore stays the Helios list until a
  species is loaded, which keeps `plantarch.load.models` equal to Helios; `heliades.species.available_species()` lists
  the files. Batch builder, fast mode and canopy builds go through `loadPlantModelFromLibrary` and needed no change.
  A species inherits the template's build-parameter declarations (so `tiller_count` works for barley).
* **`from:` resolves to a shoot type defined earlier in the file first**, then the template's: the eggplant's
  `branch` is a copy of the *eggplant* mainstem with fewer nodes, not of the tomato's.
* **Generic builder draws the base rotation right to left** (roll, yaw, pitch), as GCC evaluates the library's
  `make_AxisRotation(randu(), randu(), randu())`; angles are radians with a `'<k>pi'` form that reproduces
  `2.f * M_PI` and `0.05f * M_PI` exactly.
* **Organ hooks are cached per (species, organ, description)** so identical descriptions share one function pointer and
  therefore one prototype cache, as a C++ function would.
* **Distribution on a generator-less parameter** (`leaflet_scale`, `intercalary_leaflet_scale`, set by `operator=` in
  `PhytomerParameters()`) gets the Context generator; otherwise its first `val()` would raise.
* **Leaf textures** are generated from the outline in the species file, written by our own PNG writer (deterministic
  bytes for a given zlib), committed, and tested to equal the tool's output pixel for pixel. The mask is hard (alpha
  0 / 255) because Helios treats alpha < 250 as transparent. New species therefore depend on no image of unclear
  licence: generated images, or Helios's LGPL assets by name.

## Cucumber from the tomato template (deliverable 2)

`defs/cucumber_from_tomato.yaml` sets the 53 parameter values in which Helios's cucumber differs from its tomato
(found by a field-by-field diff of the canonical ShootParameters dumps), plus the child shoot types, the two
prototypes, the creation / callback functions and the builder, each with the source Helios gives it: 3 cited keys
(`kahlen_chen_2015`, `saba_2026`, `english_fruit_grades_2025`, cited "as cited by Helios 1.3.98" with the Helios key,
because Helios gives only keys), `judged` where Helios writes "set by the species, judged", and `helios_cucumber` for
the values Helios sets without a mark that belong to its assets (leaf aspect / offset / image, OBJ fruit and flowers).

How each non-parameter part is expressed:

| Helios cucumber | species file |
|---|---|
| shoot type `main`, no child shoots, tomato's `mainstem` dropped | `main: {from: mainstem}`, `child_shoot_types: {}`, `drop_shoot_types: [mainstem]` |
| `CucumberMainPhytomerCreationFunction` = `TomatoPhytomerCreationFunction` + bump map | 4 generic rules (`kill_buds` x2, `leaf_scale_ramp`, `internode_scale_ramp`) + `leaf_bump_map` |
| `CucumberMainPhytomerCallbackFunction` | `harvest_ripe_fruit` (generic) + `high_wire_lowering` (named rule) |
| `CucumberFlowerPrototype` / `CucumberFruitPrototype` | `{library: ...}` |
| `buildCucumberPlant` | `builder: generic` + build rule `high_wire_string` |

* **Named, not declarative**: the high-wire lowering and the string of attraction points are cucumber-specific code
  (path of the laid stem, bisection along it, sliding the string). Writing them as data would be absurd; they are the
  rules `high_wire_lowering` / `high_wire_string`, which call the ported cucumber functions. To make the callback
  composable, `library/cucumber.py`'s `CucumberMainPhytomerCallbackFunction` was split into
  `cucumberHarvestFullSizeFruit` + `cucumberLowerAndLeanStem` (the same statements, called in the same order).
* **Prototypes by library name, not `obj_variants`**: the generic `obj_variants` form reproduces the cucumber's fruit
  and flower prototypes exactly (same draw, same mesh: `test_obj_variants_reproduce_the_cucumber_prototypes`), but the
  `load` parity case compares the canonical shoot-parameter dump, which prints the function *name*
  (`CucumberFruitPrototype` on Helios). The library form keeps that name.

Parity (`python -m heliades.parity plantarch.species`), Heliades species file vs Helios 1.3.98 library cucumber,
Context seeds 1..8, 0 ulp:

| case | tier | seeds | result |
|---|---|---|---|
| `plantarch.species.cucumber_from_tomato.load` (draw counts after 0/1/2 loads + ShootParameters JSON) | exact | 8 | PASS |
| `...age0_full` (snapshot incl. hidden prototypes) | ulp 0 | 8 | PASS |
| `...age0_attrs` (materials, primitive / object data, polymesh faces) | exact | 8 | PASS |
| `...steps` (2-day steps to day 30: draws, XML, shoots, tubes, leaves; final snapshot) | ulp 0 | 8 | PASS |
| `...ages` (direct builds at 20, 40, 60, 90, 120, 165 d: bud states, XML, ..., snapshot) | ulp 0 | 48 | PASS |
| `...bump_maps` (leaf material + bump map at day 0 and 30) | exact | 16 | PASS |

The tomato's creation function written as the four generic rules also grows the library tomato bit-identically
(`tests/species/test_rules.py::test_tomato_creation_function_as_rules`).

## What the format cannot express yet

* Growth logic outside the rule registry (by design: a rule is reviewed Python). Rules exist for bud killing by node /
  rank, seedling ramps, bump maps, harvest, high-wire training and any library function by name.
* Builders other than "generic" (one base stem) and "template"; e.g. a tree with a prescribed trunk needs
  `builder: template` with a tree template.
* Leaf texture series (age-staged images), per-leaflet textures generated for compound leaves, class maps for
  generated leaves.
* Organ shapes beyond OBJ assets, ellipsoids and corollas: pods, awned spikes, panicles, umbels.
* Per-species temperature response: thresholds are degree-days at the model's one per day.
* Template-specific constants inside library functions (the wheat creation function's sheath / blade ratios, the
  cucumber's wire height) are not parameters; a species reusing such a function inherits them.

## Open issues

* Barley reuses the Helios wheat spike OBJ (scaled): no long awns, wrong spikelet arrangement for two-row barley.
* Barley shows no seed-to-seed variation in the measured traits: the wheat template's randomness is mostly in angles.
  Adding distributions is the calibration step.
* The eggplant's sympodial habit is modelled as indeterminate shoots (a determinate tomato-style shoot stops at its
  first flower, which stalled the plant at ~60 d).
* The gallery is matplotlib (per-primitive polygons, texel colour at the UV centroid): fine for eyeballing, slow for
  plants above ~200k primitives.
* The timing traits step one day at a time from age 0 (barley ~10 s per seed); good enough for the test, not for large
  sweeps.
